# Development

## Setup
Requires `uv`, Node 22, and (optional) Docker.

    make setup          # uv sync + npm ci + pre-commit hooks
    uvx pre-commit install --hook-type pre-commit --hook-type pre-push   # hooks only

## Run
    make dev-api        # FastAPI on :8000
    make dev-web        # Vite on :5173, proxies /api -> :8000

The frontend defaults to `VITE_API_MODE=mock` (in-browser backend, fully static). Use `VITE_API_MODE=live` to talk to the API.

## Run against the chain adapter (`CHAIN_MODE=l1`)
Default is `CHAIN_MODE=sim` (in-memory chain, no setup). To run the API on a Guardian L1:

    make contracts-deps && (cd contracts && forge build)   # Foundry: ~/.foundry/bin
    make l1-local-bootstrap                                # fresh local Guardian L1 + deploy + seed policy v1 + hand over + verify (~2.5 min)
    cd Backend && uv run --env-file .env.l1-local uvicorn guardian.main:app --port 8100
    cd Backend && uv run python ../infra/l1/e2e_scene4.py  # scene 4 through the API on the real node (optional)
    make l1-local-down                                     # always stop the network when done

`make l1-local-bootstrap` is `l1-local-up`, then `deploy-contracts` (the Deploy, Seed and Handover scripts in `contracts/script/`), `VerifySeed` and `verify-handover` (`VerifyHandover` fails if the deployer still has any role or power). It also writes `Backend/.env.l1-local` (CHAIN_MODE, DEMO_MODE, DEPLOYMENTS_FILE, GUARDIAN_SEED_FILE and one `L1_KEY_<SEED_ID>` per demo actor, generated by `infra/l1/local_env.py` from the PUBLIC `test ... junk` mnemonic; ignored by the VCS) and `Backend/deployments/local-l1.json` (addresses only, ignored too). The key and Council addresses the L1 genesis enables are the roster addresses, not the placeholders in `Backend/seed/may_labs.json`, so the script also writes `infra/l1/seed.l1-local.json` and the backend reads it through `GUARDIAN_SEED_FILE`.

Other targets: `make l1-policy-v2` (policy v2 through the Council), `make l1-local-checks` (T15 and T8 against the real precompiles; run `l1-policy-v2` first), `make l1-deploy|l1-seed|l1-handover` (single steps), `make verify-handover`. `NETWORK=fuji I_UNDERSTAND=fuji make deploy-contracts` targets Fuji and needs `RPC_URL`, `DEPLOYER_PK`, `SEED_FILE`, `TOP_UP_OPERATOR`, `L1_KEY_COUNCIL_TRANG|LAN|HUY` in the environment (see `infra/l1/contracts.sh`); it writes `Backend/deployments/fuji-l1.json` and has not been run (no funded Fuji key, no Fuji L1 yet).

Seeding goes through real Council proposals, so the vault's `policyVersion` is not 1 on a real deployment: it is 4 after the bootstrap (1 + two seed proposals + the top-up operator proposal) and one more after policy v2. The sim and the anvil tests still start at 1. The deployments file records that number as `policyBaseline` (`make l1-baseline`, part of `deploy-contracts`) and the API sends `policyLabel = policyVersion - policyBaseline + 1`, which is what the UI shows (v1 at the start, v2 after the merge).

### Demo reset on the L1 (`make demo-reset`)
With the API running on a bootstrapped L1 (`API_URL=http://127.0.0.1:8100 make demo-reset`; `NETWORK=local` is the default), `infra/l1/demo-reset.sh` redeploys the contract set (the vault keeps its counters per UTC day, so the old one cannot be reset) and then calls `POST /api/demo/reset`, which reloads the new deployment without a restart:

1. `ResetOpen`: after the handover the deployer has no role, so the OLD Council enables it (`setEnabled` on both AllowLists, 2-of-3 proposal).
2. `Deploy` and `Seed`: fresh tokens, DEXes, Registry, Vault, Council; policy v1 through Council proposals; 200.000 tUSDC. Written to `Backend/deployments/<network>-l1.json.next`.
3. `ResetSwitch`: the OLD Council enables every key the previous run locked (one proposal per district, approved by members with no stake in it), then hands both precompiles to the NEW Council and drops its own role (`setAdmin(new)` x2 and `setNone(old)` x2 in one proposal); the deployer moves the token minters to the new Council; the NEW Council moves the top-up operator to the ops key and removes the deployer from both lists; filler proposals (proposed and cancelled) bring the new Council's counter to 11, so request #12 gets id 12 and request #13 (move `key_agent_rebalance` to `huy`, subject `huy`, so Huy is conflicted) gets id 13; both are seeded by `POST /api/demo/reset` on the sim and on the L1, and the scene-3 merge is then proposal #14.
4. `VerifySeed`, `VerifyHandover`, a check that the old Council has no role left, `policyBaseline`, atomic rename of the file, `POST /api/demo/reset`.

Each phase is timed in the output; a failed run leaves the live file untouched, and a run that died after the switch resumes from the `.next` file. `NETWORK=fuji I_UNDERSTAND=fuji make demo-reset` uses the same steps with the variables listed in `infra/l1/contracts.sh`; it has not been run. The old Council can hand over the precompiles only because `GuardianCouncil` accepts `setAdmin(successor)` to a contract other than itself (never to an externally owned account).

The anvil suites (`uv run pytest tests/chain_l1 tests/conformance`, need Foundry; they skip without it) keep running in CI. Startup errors name the missing variable or file; `DEMO_MODE` is refused on a chain id outside `DEMO_CHAIN_IDS` (default anvil 31337 and local L1 424242). `POST /api/demo/reset` on L1 reloads the deployment that `make demo-reset` just wrote (below). Details: `docs/modules/chain-adapter/README.md`.

### End-to-end run of scenes 1-5 on the real L1 (`make e2e-l1`, OPS-004)
`make e2e-l1` (`infra/l1/e2e-l1.sh`) reuses the running local L1 or bootstraps one, starts the API on `E2E_PORT` (default 8100), then runs twice: `make demo-reset` followed by `Backend/tests/e2e/scene_all.py` against the API. The scene body is the same file the sim runs in the regular pytest run (`make e2e`, `Backend/tests/e2e/test_scene_all.py`), so the numbers cannot drift between sim and chain. It asserts the spec tables: scene 1 (7 districts, R1 on `minh`), scene 2 (20.000/20.000/100.000 at 5 %; 60.000/60.000/140.000 at 7 %), scene 3 (merge 100.000 -> 30.000, Lan proposes, Lan + Trang approve, label v2, 5 keys, cap 30.000), scene 4 (agent 5.000, steps 1-5 per section 4.3, district spent 25.000, attacker 20.000, Lan locks, `readAllowList` 0 for the 5 keys read with `cast`, step 7 `BLOCKED_AT_PROTOCOL` without a hash), scene 5 (request #12 30.000 -> 130.000 and 1,5 % -> 6,5 %; request #13 Huy 40.000 -> 60.000, Huy's approve gives HTTP 409 `CONFLICT_OF_INTEREST` and the same call straight on the Council reverts with `ConflictOfInterest()`). Output: one pass/fail table per pass, the tx hashes per step, and the duration of every step; exit code 1 on any mismatch. Always finish with `make l1-local-down` (or run with `E2E_TEARDOWN=1`). CI: the manual workflow `E2E on the local Guardian L1` (`workflow_dispatch`, `.github/workflows/e2e-l1.yml`) runs the same target; regular CI only runs the sim half.

Troubleshooting:
- Cold boot, `tx exceeds current gas capacity: N > 0`: a freshly started local P-Chain has no fee capacity for a short while. `l1-local.sh up` waits `BOOT_WAIT` (30 s) and retries `blockchain deploy` three times, 20 s apart; if it still fails, `make l1-local-down` and run again.
- `extraData` errors from web3 (`The field extraData is 86 bytes, but should be 32`): Subnet-EVM headers carry the dynamic-fee window; `chain/client.py: make_web3` injects `ExtraDataToPOAMiddleware`. Any new script that builds its own Web3 against the L1 needs the same middleware (anvil does not show it).
- `something already listens on port 8100`: set `E2E_PORT`, or stop the old uvicorn.
- Reset failed halfway: re-run `make demo-reset` (a finished set in `Backend/deployments/local-l1.json.next` is resumed).

Repository setting: Settings > Pages > Source = "GitHub Actions".
